01Why this exists

Marquee shells out to ffmpeg/ffprobe as separate subprocesses to render slideshows. Today it finds them on your PATH — which works on your dev Mac (Homebrew) but fails on any clean Mac with "FFmpeg not found." That's a hard distribution blocker: a notarized app a normal person downloads can't render. E5.S7 fixes it by shipping a signed copy of FFmpeg inside the app bundle.

What the agent already built (no action needed)

  • Resolution order — a new ffbin.py prefers a bundled binary (via env var) and falls back to PATH. The standalone CLI behavior is unchanged.
  • Bundle wiring — Tauri ships ffmpeg+ffprobe as bundle resources; the binaries are fetched at build time and never committed to the repo.
  • CI vendor + sign — release.yml downloads, verifies, and signs both binaries inside-out so the existing codesign --deep --strict gate (from E5.S2) now covers them.
  • Fail-closed guards — the vendor script refuses any build that advertises --enable-gpl/--enable-nonfree, or that's missing a capability Marquee uses (h264_videotoolbox, aac, drawtext, zoompan, …).

02What's needed from you

Three things, in order. None can be faked by an agent — they need your Apple signing identity and your judgment on the build source.

  • 1Pick an LGPL static arm64 FFmpeg + ffprobe build that includes h264_videotoolbox and drawtext. (See §05 build sources and §04 license.) Download the ffmpeg.zip and ffprobe.zip.
  • 2Compute each archive's SHA-256 and set four repo variables. CI refuses to run until all four are present (this is deliberate — see §06).
  • 3Run one cert-bearing build + prove it. Trigger release.yml via workflow_dispatch with your Apple secrets, confirm the guards pass and codesign --verify --deep --strict accepts the signed binaries, then open the notarized app on a Mac with no ffmpeg on PATH and complete a render.

03The license situation

Not legal adviceThis is a practical summary to make the decision tractable — for a commercial release, a quick sanity check with counsel on the bundled-binary obligation is cheap insurance.

FFmpeg's core is LGPL v2.1. It only becomes GPL when built with certain optional components — most notably libx264 and libx265 (the software H.264/H.265 encoders). The good news for Marquee:

Why Marquee qualifies for the LGPL path

  • You encode with h264_videotoolbox — Apple's hardware encoder. It is not a GPL component, so you don't need libx264 at all. Drop x264/x265 and the build stays LGPL.
  • drawtext needs libfreetype, which is LGPL-compatible — fine to include in an LGPL build.
  • You invoke FFmpeg as a subprocess, not by linking libav* into Marquee. That keeps FFmpeg's license off your application code entirely; the obligation is only about the bundled binary itself.

What an LGPL binary obliges you to do

  • Include attribution, e.g. "This software uses libraries from the FFmpeg project under the LGPLv2.1."
  • Make the corresponding FFmpeg source available (host the exact source/version you bundled, or link to it).
  • Document how it was built (the configure line). A pinned, reproducible build source makes this trivial.
AvoidA GPL FFmpeg build (anything with --enable-gpl / x264 / x265) would pull copyleft obligations onto distribution and is the wrong choice for a closed-source paid app. --enable-nonfree builds are not redistributable at all. The CI guard rejects both — but pick right at the source so you never hit the wall.

04The decision you actually have to make

Which build source do you standardize on? The honest catch (flagged by the implementing agent): a prebuilt, verified, LGPL, static, arm64 macOS build that also includes drawtext is not a settled, obvious artifact. Most convenient prebuilt macOS binaries are GPL (they bundle x264). Your realistic options:

  • A — Find a prebuilt LGPL build that passes the guards (fastest, if one exists for your needs). Verify its configure line shows no --enable-gpl and includes --enable-videotoolbox --enable-libfreetype.
  • B — Build once from source with exactly the flags you need (most control, guaranteed-clean license, reproducible — best for a product you'll ship repeatedly). Host the resulting zips yourself and pin them.

Recommendation: for a product you'll re-release, B (build-once, self-host, pin) is the durable answer — it makes the LGPL source-availability obligation trivial and removes dependence on a third party's "latest". Use A only if you find a build whose configure line you can actually inspect.

06What you should know

Why the SHA pins are mandatory During review, the bot caught a real security-high issue: the CI job downloads and executes a binary from a third-party host, inside a job that holds your Apple signing secrets. Without a hash pin, a compromised or swapped upstream binary could run in that trusted context. The fix made the script refuse to run unless both SHA-256 values are set — so a tampered download fails the hash check instead of executing. This is why CI is fail-closed and why you pin a versioned URL, not "latest".

  • Bundle size grows ~80–120 MB. A static FFmpeg is large; expect the notarized .app (and your download) to jump accordingly.
  • "latest" URLs are a trap. They change under you, breaking both the hash pin and the LGPL "document the exact build" obligation. Pin a versioned artifact.
  • The guard is your safety net, not your chooser. It rejects GPL/nonfree and missing-capability builds — but you still want to pick an LGPL build deliberately so the first cert-bearing run passes instead of failing the guard.
  • Notarization may surface an entitlement. Spawning a child process is normal, but if the notary log names a missing entitlement, that's the one thing to add — flagged in the PR as a watch-item.
